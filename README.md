# testtgbot

Тестовое задание: Telegram-бот, через который администратор размещает товары, и каталог на Next.js,
который открывается и в браузере, и как Telegram Mini App.

**Прод:** https://testtgbot.riakovlev.ru

## Стек

| Часть | Технология |
|---|---|
| Фронтенд | Next.js 16 (App Router), SSR на каждый запрос |
| Бэкенд | FastAPI, SQLAlchemy (async) + Alembic |
| Бот | aiogram 3, webhook, FSM в Redis |
| БД | PostgreSQL |
| Картинки | MinIO (S3) |
| Состояние бота | Redis |
| Балансировщик | Caddy |

## Схема

```
Telegram ──webhook──┐
браузер / Mini App ─┤
                    ▼
          Caddy (lb) :80 ──────────────────────────────────┐
           ├─ /tg/*    → bot  ×N ──► Redis (FSM, dedup апдейтов)
           │                   └──► /api (через lb)
           ├─ /api/*   → api  ×N ──► PostgreSQL, MinIO
           ├─ /media/* → MinIO (бакет products, публичное чтение)
           └─ /*       → web  ×N ──► /api (через lb)
```

## Как это работает

- **Разместить товар.** Админ (его ID в `ADMIN_IDS`) нажимает «Создать товар» и одним сообщением
  отправляет фото с подписью. Подпись становится названием. Фото с подписью принимается и без кнопки.
  Бот скачивает фото и отправляет его в `POST /api/products`. API кладёт файл в MinIO, а запись — в PostgreSQL.
- **Каталог.** На `/` страница с заголовком «Каталог» и списком товаров. Если страница открыта в Telegram,
  подключённый `telegram-web-app.js` вызывает `ready()` и `expand()`.
- **Остальным пользователям** бот на любое сообщение отвечает «У меня есть товар» и показывает кнопку
  Mini App. Кнопка меню чата тоже открывает каталог.

## Отказоустойчивость (stateless)

Каждый сервис работает в нескольких репликах (`API_REPLICAS`, `WEB_REPLICAS`, `BOT_REPLICAS`, по умолчанию 2).
Состояние хранят только PostgreSQL, MinIO и Redis.

- **Бот работает через webhook, а не polling.** Polling (`getUpdates`) допускает только одного читателя,
  а webhook раздаёт апдейты по репликам через балансировщик.
- **Шаги диалога админа** хранятся в Redis (`RedisStorage`), поэтому «Создать товар» и само фото может
  обработать разные реплики.
- **Повторные апдейты.** Telegram повторяет webhook, если не дождался ответа. `SET NX` по `update_id`
  в Redis гарантирует, что апдейт обработается один раз.
- **Защита от дублей при создании товара.** Ключ идемпотентности `tg:<chat>:<message>` закреплён
  уникальным индексом, поэтому повтор запроса не создаёт второй товар.
- **Миграции и создание бакета** выполняет одноразовый контейнер `migrate`. Реплики API стартуют после него,
  поэтому не конкурируют за схему. Дополнительно стоит advisory-lock.
- **Caddy находит реплики через DNS compose** (`dynamic a`, обновление раз в 1 с). При отказе реплики
  он повторяет запрос на другую (`lb_try_duration`) и выводит упавшую из ротации.
- **Сервисы не держат файлов и кэша.** Каталог рендерится на каждый запрос, картинки лежат в S3.

## Запуск

```bash
cp .env.example .env      # заполнить BOT_TOKEN, ADMIN_IDS, секреты
./ctl.sh start            # docker compose up --build → http://127.0.0.1:5218
./ctl.sh status | logs [service] | stop
```

Если `WEBHOOK_BASE_URL` пустой, бот работает через long polling. Это подходит только для локальной разработки,
и `ctl.sh` тогда сам поднимает одну реплику бота. Без `BOT_TOKEN` бот не запускается, остальной стек работает.

Изменить число реплик: `docker compose up -d --scale api=3 --scale web=3 --scale bot=3`.

## Проверка

```bash
NODE_PATH="$(npm root -g)" node e2e/check.mjs
```

Сценарий проверяет:

- создание товара через API, включая 401 без токена и идемпотентность;
- отдачу картинки из MinIO;
- распределение запросов по репликам (заголовок `X-Instance`);
- каталог в браузере (Playwright);
- переживание отказа: после `docker kill` одной реплики api и одной web API и каталог продолжают отвечать.

## Деплой

`./deploy.sh` копирует исходники на сервер через rsync и выполняет там `docker compose up -d --build`.
Перед первым деплоем нужно один раз заполнить `.env` на сервере. Наружу TLS отдаёт nginx хоста,
он проксирует запросы на `127.0.0.1:$LB_PORT`.
